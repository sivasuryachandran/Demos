YAML scaffold
How the volume was possible

I didn't hand-write all of that.

arctest ships an agent toolchain, and each one owns a single artifact type. Porting a suite means feeding the right agent the right input — and knowing enough to check what comes back.

Robot migrator

Converts .robot files into arctest YAML — maps old keywords onto framework actions, reports what has no equivalent yet, then generates iteratively.

Topology builder

Authors the logical topology: network roles, which config template each role gets, and the variables they share.

Testbed builder

Wires that logical topology onto real lab devices — hostnames, IPs, credentials, interface mappings.

Suite orchestrator

Turns a plain-language test plan into suite YAML, validated against the action registry so it can't invent steps that don't exist.

The split matters: one topology, many testbeds. The logical design is written once, then mapped onto whichever rack is actually free.

What migration taught me

A test that passes isn't the same as a test that's true.

Porting a suite means reading every assertion closely enough to move it. Which is also close enough to notice when one was never really checking anything.

device truth rerun
Writing it is the easy half

Running it, auditing it, and finding out why it broke.

A generated suite is a draft. These are the agents that turn a draft into something you'd trust in a regression run — and they're where I spent most of my time.

Build agent

The conductor. Builds a whole new suite end to end from a feature spec by orchestrating the specialists — and writes no YAML itself.

arctest debug

The loop I lived in: run → classify the failure → fix the test, action or template → rerun. Diagnoses against device truth over SSH, not against what the YAML claims.

arctest audit

Checks a finished suite for drift between tests, topology, testbed and actions — and keeps going until a re-audit produces zero edits.

arctest triage

Root-cause work on the hard ones: live devices, tech-support tarballs, core dumps, source. Read-only unless you explicitly authorise a change.

The distinction that mattered most: debug asks "why is this test failing?" — triage asks "why is this device behaving like that?" Reaching for the wrong one is exactly how you end up fixing a test to hide a product bug.
spec device
What automation taught me

You can only automate what you already understand.

A suite is a set of claims about correct behaviour. Writing one forces you to admit exactly how much of that behaviour you actually know.

Have
The specification

What the protocol is supposed to do, in prose.

→
Missing
What it actually does here

On this build, this hardware, this topology. Nobody wrote this down.

→
Want
A suite that asserts it

Precise enough to fail for the right reason.

I hit that gap directly. One finding looked like a bug, but might equally have been build-dependent behaviour — and I couldn't tell which. So I left it failing and flagged it for a human instead of "fixing" it into silence.

That isn't a testing problem. It's a knowing problem — and you don't close it by writing more YAML.

L3VPN VRF route leaking

Five VRFs. Two address families. One policy engine.

A 5-VRF physical lab topology with eBGP CE routes for IPv4 and IPv6 — then leaked routes verified across BGP Loc-RIB, VRF RIB, and SRv6 forwarding attributes: END_DT4 for IPv4, END_DT6 for IPv6.

add / remove RT change RT value no manual clears VRF recreate interface flap AF disable
Work completed

Functional, dynamic, and resilient — all three.

Route characteristics

BEST_PATH, IMPORTED_PATH, source VRF and recursive next-hop, plus correct SRv6 SID behavior for both address families.

Dynamic configuration

Add and remove import/export Route Targets, change RT values, source withdrawal and recovery — across multiple routes and multiple VRFs at once.

Lifecycle & resilience

BGP process restart, AF disable and re-enable, VRF delete and recreate, interface flap, policy object delete and recreate. Routes recover automatically — no manual BGP clears required.
